Process description

Source application: the application to add.

Target application: the application that identifies the group to use.

  1. The client sends POST /api/v0/applications/{id}/link. The path contains the source application ID.
  2. The request contains the target application ID and the link type FAMILY.
  3. The service checks caseworker access. It rejects a request that uses the same ID for both applications.
  4. The service locks both membership records. Both applications must exist and have the same office code.
  5. If neither application belongs to a group, the service creates a group. The target becomes the lead. Do not supply linkedGroupVersion.
  6. If only the target belongs to a group, the service adds the source. Supply the target's linkedGroupVersion token exactly as last read.
  7. The service checks the group ID and version before it adds the source. It rejects the request if these values no longer match.
  8. If both applications belong to the same group, the service returns success. It makes no change and stores no new event.
  9. If the source belongs to another group, the service rejects the request. The service does not combine groups.
  10. For a change, the service stores an event and updates write-side membership in the same transaction. It then returns 204 No Content.
Scope: the Axon application linking implementation. The description uses ASD-STE100-style English. Formal compliance is not certified. The animation shows a logical sequence, not processing time. The read-model update runs separately after commit; it can finish before or after the client receives the response.
